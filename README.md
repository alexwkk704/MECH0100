# AI-Driven Inverse Design of Multifunctional Metamaterials with Adaptive Stiffness

Code for an MSc thesis (MECH0100, UCL Mechanical Engineering, 2026).
Authors: Kwun Kit (Alex) Wong and ZheZhe Du. Supervisor: Dr Farooq Azam.

A forward machine-learning surrogate predicts the homogenised elastic properties
of two lattice families from geometry alone, and a two-level search inverts it:
given a required stiffness, it proposes geometries that achieve it. Proposed
designs are rebuilt and re-simulated in the full finite element chain, which is
the only unbiased test of the system.

Two architectures are studied: **ADMS**, aperiodic minimal surfaces generated by
sphere packing, and **TPMS**, periodic minimal surfaces tiled from a unit cell.

---

## Repository layout

| folder | contents |
|---|---|
| `ADMS/` | geometry generation and finite element homogenisation for the ADMS family — `ntop_batch.py`, the production driver that runs nTop headlessly, plus its input schemas, run sheet and verification |
| `TPMS/` | the same for the TPMS family — ZheZhe Du's STL export and homogenisation drivers |
| `ML/` | the numbered batch files, run in order — database build, training, holdout evaluation, model export |
| `ML/scripts/` | feature extraction, point-cloud preparation, grouped cross-validation, RF / GPR / PointNet training, export and gate checks |
| `ML/data/` | three datasets, quadratic elements only |
| `ML/Final Model/COMBINED/` | the exported four-seed forward model the inverse search consumes, plus its model card |
| `Inverse design/` | `ID_1` coarse search → `ID_2*` / `ID_3*` new-geometry generation → `ID_4` ranking → `ID_5` finite element verification |
| `Inverse design/example/` | one example geometry — the FE-verified TPMS design |
| `ML_settings.xlsx` | every path, material constant, column name, normalisation and holdout definition. Nothing is hardcoded in the scripts. |

**The folder layout is load-bearing — please do not rearrange it.** Each batch
file resolves its scripts relative to its own location, and the inverse-design
batch files reference `..\ML\`. Moving files breaks those paths.

`.gitattributes` pins `*.bat` to CRLF line endings. Without it, git rewrites
batch files on checkout and they stop running on Windows.

## Data provenance — quadratic elements only

Every dataset here was solved with quadratic tetrahedra on both families:

| file | rows | element order |
|---|---|---|
| `dataset_ADMS.csv` | 163 | quadratic |
| `dataset_TPMS_quad.csv` | 183 | quadratic |
| `dataset_COMBINED_quad.csv` | 346 | quadratic (183 TPMS + 163 ADMS) |

Earlier linear-element datasets are deliberately excluded and are blocked in
`.gitignore`. Mixing element orders makes linear tetrahedra read as roughly
6–8 % over-stiff, which would confound any comparison between the two families.
`ML_settings.xlsx` carries `element_order = quadratic` on both sides and an
`element_order_ref` tensor whose order is known, so a silent data swap aborts
the build rather than passing quietly.

## Running it

Requires Windows, Python 3.10+, and nTop with `ntopcl` on `PATH` for the
geometry and finite element stages.

```
pip install numpy scipy pandas scikit-learn matplotlib openpyxl torch trimesh
```

Run the batch files in `ML/` in numerical order. Paths resolve from
`ML_settings.xlsx` through `ML/scripts/run_paths.py` — edit the workbook, not
the scripts.

**The nTop files are not in this repository.** There are 54 of them totalling
3.2 GiB, and eight individually exceed GitHub's 100 MiB per-file limit;
compressing them does not help, because a solved file has a mesh baked in
and only reaches about 65 % of its size. They are held on OneDrive:

Point clouds, run folders and candidate geometries are excluded for the same

to show the output format.

## Scope

Only the code that produced the reported results is included. Superseded entry
points, earlier exporters and closed-out investigation scripts have been left
out.

The inverse design is a **demonstration**: one ADMS target and one TPMS target,
each rebuilt and verified by finite element analysis. It is not a validated
design tool, and targets outside the sampled property range are reported as
unreachable rather than answered.

All results are numerical. No physical testing was carried out.
